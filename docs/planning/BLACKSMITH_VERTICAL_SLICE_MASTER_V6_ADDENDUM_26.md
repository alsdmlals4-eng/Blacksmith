## 여러 중요 고객 트리거의 대기 우선순위

여러 중요 고객의 확정 등장 조건이 동시에 충족되어 대기할 경우, 고객 이름이나 코드 작성 순서가 아니라 **트리거 데이터의 우선순위 등급과 충족 시점**으로 실제 방문 순서를 결정한다.

```text
1차 정렬
→ priority_class가 높은 트리거 우선

2차 정렬
→ 같은 priority_class에서는 먼저 충족된 트리거 우선

3차 정렬
→ 같은 영업일에 충족됐다면 안정적인 생성 순번 우선
```

한 영업일에 실제로 생성할 수 있는 신규 방문 고객 요청은 기존 결정대로 최대 1개다.

## 우선순위 등급

중요 고객 트리거는 다음 3개 등급 중 하나를 데이터로 가진다.

| 등급 | 명칭 | 사용 목적 |
|---:|---|---|
| 1 | `REQUIRED_PROGRESS_OR_RECOVERY` | 진행 차단 해소, 필수 후속, 저장·복구 후 반드시 이어져야 하는 고객 |
| 2 | `FIRST_APPEARANCE_OR_REPRESENTATIVE` | 최초 등장, 대표 콘텐츠, 버티컬 슬라이스 핵심 증명 고객 |
| 3 | `REPEAT_OR_OPTIONAL_IMPORTANT` | 반복 방문, 선택적 중요 고객, 추가 관계·세계 콘텐츠 |

숫자가 작을수록 우선순위가 높다.

### 1등급: 진행 차단 해소·필수 후속

다음과 같은 트리거에 사용한다.

- 선행 거래 이후 반드시 전달돼야 하는 필수 결과 고객
- 복구된 저장에서 누락되면 진행이 막히는 후속 요청
- 핵심 시스템 안내 또는 필수 전환을 완료하기 위한 방문
- 특정 세계 결과를 정리하지 않으면 다음 진행으로 갈 수 없는 고객

1등급은 단순히 보상이 높거나 인기 있는 고객이라는 이유로 부여하지 않는다.

### 2등급: 최초 등장·대표 콘텐츠

다음과 같은 트리거에 사용한다.

- 검투사·모험가 등 대표 콘텐츠 고객의 최초 등장
- 버티컬 슬라이스에서 반드시 검증해야 하는 고객 파이프라인
- 특정 고객 유형을 처음 소개하는 요청
- 주요 제작·강화 이정표 이후 열리는 첫 고객 사건

### 3등급: 반복·선택적 중요 고객

다음과 같은 트리거에 사용한다.

- 이미 첫 거래를 완료한 고객의 반복 방문
- 추가 관계·연대기·보상 콘텐츠
- 실패·거절·만료 후 발생 가능한 선택적 재방문
- 진행을 막지 않는 확장 세계 사건

반복 방문이 대기 중인 최초 등장 고객이나 필수 후속 고객을 앞지르지 않는다.

## 고객 이름 하드코딩 금지

우선순위를 다음처럼 정의하지 않는다.

```text
검투사 > 모험가 > 수집가 > 병사
```

금지되는 구조:

- 고객 이름을 검사해 우선순위를 결정
- 고객 유형별 별도 코드 분기
- 콘텐츠 파일 순서나 enum 순서가 암묵적 우선순위가 됨
- 새 고객을 추가할 때 우선순위 코드를 수정해야 함
- 특정 고객이 항상 다른 고객보다 먼저 등장함

허용되는 구조:

```text
pending_trigger.priority_class
pending_trigger.fulfilled_operating_day
pending_trigger.sequence
```

고객이 달라도 같은 의미의 트리거는 같은 우선순위 등급을 사용할 수 있다.

## 대기 트리거 데이터

대기 중인 중요 고객 트리거는 최소 다음 정보를 저장한다.

- `pending_trigger_id`
- `trigger_definition_id`
- `customer_id` 또는 고객 유형
- `priority_class`
- `fulfilled_operating_day`
- `sequence`
- `dedupe_key`
- 트리거 충족 원인
- 선행 상태 또는 연결된 결과 식별자
- 요청 장비 종류·범주 생성에 필요한 데이터
- 활성 여부
- 실제 방문 요청으로 변환됐는지 여부

대기 상태에는 방문 고객 요청의 2영업일 기한을 부여하지 않는다.

```text
트리거 충족
→ pending 상태 저장
→ 아직 고객 방문 아님
→ 요청 슬롯 미점유
→ 기한 미시작
```

## 선정 순서

영업일 시작에 빈 방문 고객 요청 슬롯이 존재하면 다음 순서로 대기 트리거를 평가한다.

```text
1. 저장 복구·미확인 결과 정리
2. 거래·거절·만료 상태 정리
3. 활성 요청 슬롯 계산
4. 대기 중요 고객 트리거 로드
5. priority_class 오름차순 정렬
6. fulfilled_operating_day 오름차순 정렬
7. sequence 오름차순 정렬
8. 최상위 트리거 1개 선택
9. 실제 방문 고객 요청 생성
10. 선택된 대기 트리거 제거 또는 완료 처리
11. 당일 신규 요청 판정 완료 저장
```

### 같은 등급에서 오래된 순

같은 `priority_class`에서는 먼저 충족된 트리거가 우선한다.

```text
트리거 A
priority_class 2
영업일 5 충족

트리거 B
priority_class 2
영업일 7 충족

→ 트리거 A 먼저 생성
```

같은 영업일에 여러 트리거가 충족되면 저장된 안정적 `sequence`를 사용한다. 앱 재실행이나 데이터 로딩 순서에 따라 결과가 바뀌지 않아야 한다.

## 동일 트리거 중복 병합

같은 고객의 같은 의미를 가진 트리거가 반복 충족돼도 대기 항목을 무한히 쌓지 않는다.

`dedupe_key`가 동일한 활성 대기 트리거는 하나로 병합한다.

```text
동일 dedupe_key 트리거 재충족
→ 새 대기 항목 추가 안 함
→ 기존 fulfilled_operating_day 유지
→ 필요한 최신 연결 상태만 안전하게 병합
```

원칙:

- 오래 기다린 순서를 잃지 않도록 최초 충족 영업일 유지
- 중복 충족으로 우선순위를 인위적으로 높이지 않음
- 동일 보상을 여러 번 생성하지 않음
- 같은 고객의 동일 최초 등장 요청을 중복 생성하지 않음
- 앱 재실행으로 동일 트리거가 다시 적재되지 않음

서로 다른 의미의 트리거는 같은 고객이라도 별개로 대기할 수 있다. 다만 선행 상태와 상호 배타 조건을 검증해 동시에 유효하지 않은 트리거를 함께 유지하지 않는다.

## 우선순위 변경 규칙

트리거가 대기 중이라는 이유만으로 자동으로 상위 등급으로 승격하지 않는다.

- 같은 등급에서는 오래된 순서로 기아 상태를 완화한다.
- 3등급 반복 방문이 2등급 최초 등장을 추월하지 않는다.
- 2등급 최초 등장이 1등급 필수 후속을 추월하지 않는다.
- 보상 크기·장비 희귀도·고객 인기만으로 등급을 변경하지 않는다.
- 우선순위 등급 변경이 필요하면 콘텐츠 데이터 개정으로 명시한다.

진행 차단 트리거가 계속 생성돼 낮은 등급이 장기간 밀리는 문제가 실제로 발생하면 트리거 설계 결함으로 기록한다. 런타임에서 임의 승격해 숨기지 않는다.

## 슬롯 포화 시 처리

활성 방문 고객 요청이 2개이면 대기 트리거를 실제 요청으로 변환하지 않는다.

```text
대기 중요 고객 존재
+ 활성 요청 2개
→ 실제 방문 생성 없음
→ 대기 순서 유지
→ 기한 시작 없음
→ 관계·명성 패널티 없음
```

기존 활성 요청을 자동 교체하거나 거절하지 않는다.

슬롯이 영업일 도중 비어도 같은 날 중요 고객을 즉시 생성하지 않는다. 다음 영업일 시작 처리에서 다시 평가한다.

## 일반 무작위 요청과의 관계

대기 중인 중요 고객 트리거가 있고 빈 슬롯이 존재하면 중요 고객을 먼저 생성한다.

```text
대기 중요 고객 존재
→ 중요 고객 요청 1개 생성
→ 당일 일반 40% 판정 없음
→ 일반 연속 미발생 누적 유지
```

대기 중요 고객이 없을 때만 일반 40% 및 연속 미발생 보정 판정을 수행한다.

한 영업일에 중요 고객 1개와 일반 고객 1개를 함께 생성하지 않는다.

## 요청 생성 원자성

선정된 대기 트리거를 실제 방문 고객 요청으로 변환할 때 다음 상태를 하나의 원자적 결과로 저장한다.

- 선택된 `pending_trigger_id`
- 생성된 방문 고객 요청 식별자
- 요청 장비 종류·조건·보상
- 기본 2영업일 기한
- 활성 요청 슬롯 점유
- 대기 트리거 완료 또는 제거 상태
- 당일 신규 요청 판정 완료 표식
- 일반 미발생 누적 유지 상태

```text
대기 트리거 선택
+ 방문 요청 생성
+ 대기 항목 소비
+ 슬롯 점유
+ 당일 판정 완료
→ 원자적 저장
→ 이후 발생 연출
```

금지되는 중간 상태:

- 대기 트리거는 사라졌지만 요청이 생성되지 않음
- 요청은 생성됐지만 대기 트리거가 남아 다음 날 중복 생성됨
- 요청이 생성됐지만 슬롯 수에 반영되지 않음
- 당일 판정 완료 표식이 없어 앱 재실행 후 다시 생성됨
- 일반 미발생 누적이 중요 고객 생성 때문에 초기화됨

저장 실패 시 대기 트리거를 잃지 않은 이전 확정 상태로 복귀한다.

## 취소·무효화

대기 중인 트리거의 선행 조건이 더 이상 유효하지 않게 될 수 있다.

예:

- 연결된 장비가 영구 파괴됨
- 선행 세계 상태가 다른 분기로 확정됨
- 같은 목적의 거래가 다른 경로로 완료됨
- 고객 상태가 더 이상 해당 요청을 허용하지 않음

이 경우 트리거를 조용히 삭제하지 않는다.

- 무효화 원인 기록
- 보상·관계 변화 중복 적용 금지
- 요청으로 생성되기 전이므로 기한 만료 처리 금지
- 필수 진행 트리거가 무효화되면 대체 진행 경로 또는 무결성 오류 처리
- 무효화와 대기 목록 제거를 원자적으로 저장

## UI·알림

대기 트리거는 아직 실제 방문 고객이 아니므로 일반 플레이어에게 방문 요청처럼 표시하지 않는다.

- `[방문 고객]` 활성 요청 수에 포함하지 않음
- 남은 영업일 표시 없음
- 놓친 고객 알림 없음
- 방문 고객 배지 없음
- 실제 요청 생성 후에만 고객·장비 종류·2영업일 기한 표시

테스트 빌드의 진단 화면에서는 대기 트리거의 식별자·등급·충족 영업일·선정 순서를 확인할 수 있다. 정식 사용자 UI에 디버그 우선순위 숫자를 노출할 필요는 없다.

## 검증 시나리오

버티컬 슬라이스와 구현 테스트에서 최소 다음을 검증한다.

1. 1등급·2등급·3등급이 동시에 대기하면 1등급 먼저 생성
2. 같은 등급 두 개는 먼저 충족된 트리거 먼저 생성
3. 같은 영업일 충족 트리거는 재실행 후에도 동일 순서 유지
4. 동일 `dedupe_key` 재충족 시 대기 항목 하나만 존재
5. 슬롯 2개 상태에서 대기 트리거 기한이 시작되지 않음
6. 슬롯 해제 후 다음 영업일에 최상위 트리거 정확히 1개 생성
7. 중요 고객 생성일 일반 40% 판정 미수행 및 누적 유지
8. 요청 생성 도중 앱 종료 후 중복 고객·중복 보상 없음
9. 대기 트리거 무효화 시 요청·만료 결과가 잘못 생성되지 않음
10. 신규 고객 콘텐츠 추가 시 고객 이름 코드 분기 없이 우선순위 지정 가능

## 현재 기획 상태 영향

이번 결정으로 해결되는 항목:

- 여러 중요 고객 트리거의 우선순위
- 같은 등급의 순서
- 동일 트리거 중복 병합
- 슬롯 포화 중 대기 처리
- 중요 고객 생성의 원자성
- 고객 이름 하드코딩 금지

아직 미정인 항목:

- 일반 요청의 고객 유형·장비 종류·보상 가중치
- 같은 장비 종류 요청의 연속 중복 억제
- 버티컬 슬라이스 대표 고객 이벤트 조합
- 일반 영업과 방문 고객 이벤트를 포함한 15~25분 세션 예산
- 반복 방문 고객의 정확한 재방문 조건

```text
PENDING_IMPORTANT_TRIGGER_PRIORITY_MODEL: DATA_CLASS_THEN_OLDEST
```

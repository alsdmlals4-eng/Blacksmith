## 결정 — 코어 재미 검증은 행동 증거와 회상 인터뷰를 함께 사용

사용자 승인:

- `권장안대로 진행`

### 확정 내용

1. 첫 코어 버티컬 슬라이스의 통과 여부를 단일 만족도 점수나 자유 의견만으로 판정하지 않는다.
2. 클릭 수·완료율·세션 시간 같은 행동 로그만으로도 판정하지 않는다.
3. 플레이 중 관찰되는 행동 증거와 플레이 직후 회상 인터뷰를 함께 사용한다.
4. 행동과 인터뷰가 서로 일치할 때 해당 핵심 재미 가설의 지지 증거로 본다.
5. 행동과 인터뷰가 충돌하면 통과를 보류하고, 기억 왜곡·UI 오해·우연한 성공·사회적 바람직성 응답·로그 해석 오류 가능성을 검토한다.
6. 모든 플레이어가 동일 행동을 보여야 한다고 고정하지 않는다. 정확한 표본 수·통과 비율·반복 횟수는 `RECOMMENDED_DEFAULT / TEST_VALUE`다.
7. 정량 지표는 실패·이탈·반복 노동·판단 정지 구간을 찾는 보조 증거이며, 핵심 재미를 단독 증명하지 않는다.
8. 인터뷰는 플레이어가 자신의 선택·작품 정체성·결과 인과·다음 행동 의도를 스스로 설명할 수 있는지 확인한다.
9. 진행자가 정답을 유도하거나 시스템 용어를 먼저 알려주지 않는다.
10. 같은 플레이어에게 질문 순서·표현을 과도하게 바꾸지 않고, 테스트 버전별 질문 계약을 기록한다.
11. 반복적으로 실패하는 연결부는 수치 조정만으로 덮지 않고 구조·피드백·정보 설계 문제인지 적대적으로 검토한다.
12. 긍정 발언과 실제 행동이 다를 경우 긍정 발언만으로 통과시키지 않는다.

### 필수 행동 증거 범주

최소 검증 범주는 다음과 같다.

1. `강화 판단`
   - 플레이어가 최소 한 번 강화 지속과 중단 사이에서 실제로 고민한다.
   - 공개된 비용·위험·작품 상태를 확인한 뒤 선택한다.
2. `작품 정체성 기억`
   - 일반 수식어 A·B와 주요 정밀강화 선택을 기억하거나 자신의 말로 구분한다.
3. `인과 이해`
   - 납품 결과에서 어떤 강화·수식어·지원 선택이 기여했는지 설명한다.
4. `생애 환류`
   - 같은 UID의 재방문 이후 다음 강화·복원·재납품 행동을 자발적으로 선택하거나 명확한 의도로 제시한다.
5. `피로도·날짜 이해`
   - 피로도를 단순 대기 장벽이 아니라 오늘의 작업 우선순위 자원으로 사용한다.
   - 날짜 진행이 세계 결과와 후속 작업을 연결한다고 이해한다.
6. `손상·복원 의미`
   - 실패·손상·복원이 작품 삭제나 무의미한 벌만이 아니라 새로운 생애와 목표를 만든다고 인식한다.

### 회상 인터뷰 최소 질문

질문은 정답을 포함하지 않는 중립적 표현을 사용한다.

- `이 작품이 다른 작품과 어떻게 달랐나요?`
- `왜 그 시점에 강화를 멈추거나 계속했나요?`
- `납품 결과에 어떤 선택이 영향을 줬다고 생각하나요?`
- `세계 결과를 본 뒤 다음에 무엇을 하려 했나요?`
- `이 작품이 같은 모습이나 다른 상태로 다시 돌아왔을 때 무엇을 느꼈나요?`
- `피로도와 날짜 때문에 어떤 작업을 먼저 하기로 했나요?`

필요 시 후속 질문은 플레이어 답변을 명확히 하는 데만 사용하며 시스템 설명이나 정답을 제공하지 않는다.

### 증거 일치·충돌 판정

```text
행동 증거 긍정 + 회상 인터뷰 일치
→ 해당 가설 지지

행동 증거 부정 + 회상 인터뷰 부정
→ 해당 연결부 실패 가능성 높음

행동 증거 긍정 + 인터뷰 불일치
→ 우연한 행동·UI 오해·기억 실패 검토

행동 증거 부정 + 인터뷰 긍정
→ 예의상 긍정·의도와 실제 행동의 괴리 검토

증거 충돌
→ 통과 보류
→ 원인 가설 설정
→ 최소 변경
→ 재검증
```

### 통과·실패 원칙

- 만족도 평균 하나로 전체 코어를 통과시키지 않는다.
- 모든 범주를 단일 총점으로 합쳐 원인을 숨기지 않는다.
- `강화 판단`, `작품 정체성`, `인과 이해`, `생애 환류`, `피로도·날짜`, `손상·복원 의미`를 분리해서 기록한다.
- 특정 범주가 반복 실패하면 전체 루프의 어느 연결부가 끊겼는지 우선 수정한다.
- 표본이 작을 때는 통계적 일반화를 주장하지 않고 탐색적 증거로 표시한다.
- 정확한 통과 비율과 표본 수는 첫 테스트 프리셋과 대상 사용자 정의 후 별도 승인한다.

### 보호 조건

- 진행자가 플레이 중 선택 이유를 반복 질문해 행동을 바꾸지 않는다.
- 플레이어가 막혔을 때 제공한 도움과 시점을 기록한다.
- UI 버그·성능 문제·입력 오류가 재미 판정에 미친 영향을 분리한다.
- 숙련도·장르 경험·테스트 맥락 차이를 무시하지 않는다.
- 한 명의 강한 긍정 또는 부정 의견을 전체 사용자 결론으로 확대하지 않는다.
- 인터뷰 답변을 게임 용어 사용 여부만으로 평가하지 않고 자신의 말로 인과와 의도를 설명하는지 본다.
- 관찰자가 기대한 행동과 다르다는 이유만으로 실패 처리하지 않고 프로젝트 핵심 목표와 연결되는 대안 행동인지 검토한다.

### 벤치마킹 적용

- Unity Learn은 플레이테스트가 단순히 게임이 재미있는지 묻는 것이 아니라 설계의 특정 부분에 대한 유용한 정보를 체계적으로 수집하는 과정이라고 설명한다.
- Unity의 사용자 피드백 자료는 여러 사용자 테스트와 비교 가능한 응답을 통해 개선 결정을 지원하도록 권장한다.
- Steam Playtest는 본 게임의 리뷰·위시리스트 등에 직접 영향을 주지 않는 별도 환경에서 실제 사용자 경험과 데이터를 수집할 수 있게 한다.
- Blacksmith는 특정 도구나 플랫폼 운영을 현재 필수 구현으로 확정하지 않고, `구조화된 관찰 + 중립적 회상 인터뷰 + 반복 검증` 원칙만 채택한다.

### 정본 우선순위

본 결정은 다음 표현보다 우선한다.

- 플레이어가 재미있다고 답하면 코어 검증을 통과한다는 해석
- 완료율·클릭 수·세션 시간만으로 핵심 재미를 증명한다는 해석
- 플레이어 한 명의 반응을 전체 사용자 결론으로 일반화하는 방식
- 행동과 인터뷰가 충돌해도 평균 점수로 상쇄하는 방식
- 진행자가 정답과 시스템 의도를 먼저 설명한 뒤 이해도를 측정하는 방식

정리 후 표준 문구:

> Blacksmith의 코어 재미는 행동 로그 또는 만족도 한쪽만으로 검증하지 않는다. 강화 판단, 작품 정체성 기억, 결과 인과 이해, 같은 UID 생애 환류, 피로도·날짜 우선순위 사용과 손상·복원의 의미를 플레이 중 행동으로 관찰하고, 직후 중립적 회상 인터뷰로 확인한다. 두 증거가 충돌하면 통과를 보류하고 원인을 수정한 뒤 재검증한다.

## 동시 활성 방문 고객 요청 수

`[방문 고객]` 요청 이벤트는 **동시에 최대 2개까지 활성화**할 수 있다.

활성 요청이 0개 또는 1개일 때는 신규 방문 고객 요청이 발생할 수 있다. 활성 요청이 2개이면 추가 요청 발생 판정을 보류하며, 기존 요청 중 하나가 거래 완료·명시적 거절·기한 만료로 종료된 이후 다시 신규 요청 발생 자격을 얻는다.

```text
활성 요청 0개
→ 신규 요청 발생 가능

활성 요청 1개
→ 신규 요청 발생 가능

활성 요청 2개
→ 추가 요청 발생 보류
→ 기존 요청 1개 종료
→ 신규 요청 발생 가능 상태 복구
```

이 제한은 요청 UI 단순화를 위한 표시 제한이 아니라 실제 활성 요청 상태의 상한이다.

## 활성 요청의 정의

다음 상태는 활성 요청 수에 포함한다.

- `미확인`
- `활성`
- `제안 검토 중`

다음 상태는 활성 요청 수에 포함하지 않는다.

- `거래 완료`
- `거절`
- `만료`
- `후속 진행 중`
- `후속 완료`

거래 이후 생성된 경기·원정·전시·임무 같은 후속 세계 활동은 `[세계]`의 별도 진행 상태이며, 방문 고객 요청 활성 한도를 계속 점유하지 않는다.

```text
방문 고객 요청
→ 거래 완료
→ 요청 슬롯 해제
→ 후속 세계 활동은 별도 유지
```

## 요청 슬롯 계약

### 최대 수

- 동시 활성 요청 최대치: 2개
- 이름 있는 중요 고객도 동일한 최대치에 포함
- 일반 고객·이름 있는 고객을 위한 별도 숨은 슬롯 없음
- 튜토리얼 요청도 활성 상태라면 동일한 슬롯을 사용
- 테스트 전용 요청도 실제 활성 상태를 검증할 때는 동일한 제한을 적용

### 슬롯이 가득 찬 경우

활성 요청이 2개인 동안 신규 방문 고객 발생 판정은 다음처럼 처리한다.

- 신규 요청을 생성하지 않는다.
- 생성되지 않은 요청에 기한을 부여하지 않는다.
- 숨은 대기열에서 남은 영업일을 감소시키지 않는다.
- 기존 요청을 자동 교체하지 않는다.
- 오래된 요청을 자동 거절하거나 만료시키지 않는다.
- 중요 고객을 위해 일반 요청을 강제로 삭제하지 않는다.
- 플레이어에게 “놓친 고객” 패널티를 부과하지 않는다.

즉, 용량이 찬 상태에서는 아직 실제로 방문하지 않은 것이다.

## 신규 요청 발생 자격 복구

활성 요청 중 하나가 다음 상태로 확정되면 요청 슬롯이 해제된다.

- 거래 완료
- 명시적 거절
- 기한 만료

슬롯 해제와 신규 요청 발생은 같은 비가역 처리로 묶지 않는다.

```text
기존 요청 종료 저장
→ 활성 요청 수 재계산
→ 다음 신규 요청 발생 판정 시 자격 확인
```

원칙:

- 요청 종료 저장이 완료되기 전에 신규 요청을 같은 슬롯에 덮어쓰지 않는다.
- 앱 종료·복구 중 슬롯 상태가 중복 해제되지 않는다.
- 한 요청 종료로 두 개 이상의 신규 요청이 동시에 생성되지 않는다.
- 슬롯이 비었다고 즉시 신규 요청을 강제 생성하지 않는다.
- 정확한 신규 요청 발생 시점은 후속 발생 빈도 결정에 따른다.

## 두 요청의 독립성

동시에 활성화된 두 요청은 각각 독립된 상태와 기한을 가진다.

각 요청별 저장 항목:

- 요청 식별자
- 고객 식별자 또는 고객 유형
- 요청 장비 종류·범주
- 최소 조건
- 선호 방향
- 사용 목적·야망
- 보상
- 생성 영업일
- 남은 영업일
- 확인 여부
- 현재 상태
- 선택 중인 보관함 제품
- 거래·거절·만료 결과 적용 여부
- 후속 활동 연결 상태

한 요청에서 발생한 다음 행동이 다른 요청을 변경하지 않아야 한다.

- 제품 제안
- 일반 판매에 의한 후보 제품 제거
- 거래 완료
- 명시적 거절
- 기한 감소
- 만료
- 관계 변화
- 후속 세계 활동 생성

```text
요청 A: 장검, 남은 영업일 1
요청 B: 방패, 남은 영업일 2

요청 A 거래 완료
→ 요청 A 종료
→ 요청 B의 기한·제품 후보·보상·상태 불변
```

## 장비 종류와 보상 방향의 대비

동시에 활성화된 두 요청은 운영 판단을 만들 수 있도록 서로 다른 장비 종류 또는 가치 방향을 가질 수 있다.

예시:

- 검투사: 장검 요청, 성능·명성 중심
- 수집가: 의식용 투구 요청, 희소성·역사 가치 중심
- 모험가: 방어구 요청, 내구·환경 대응 중심
- 병사: 방패 요청, 보급성·수리성 중심

다만 다음 규칙은 두지 않는다.

- 두 요청이 항상 다른 고객 유형이어야 함
- 두 요청이 항상 다른 장비 종류여야 함
- 같은 종류 요청이 동시에 절대 발생하지 않음
- 높은 보상 요청이 낮은 보상 요청을 자동 제거함

정확한 중복 방지·가중치·요청 조합 규칙은 후속 요청 생성 결정에서 확정한다.

## 같은 보관함 제품이 두 요청의 후보인 경우

일반 제품은 고객 전용이 아니므로 같은 보관함 제품이 두 활성 요청 모두에 적합할 수 있다.

```text
제품 X
├─ 요청 A에 제안 가능
└─ 요청 B에 제안 가능
```

원칙:

- 후보 표시는 예약이 아니다.
- 한 요청의 제안 검토 화면에 올려도 다른 요청 후보에서 숨기지 않는다.
- 한 요청에서 거래를 확정하면 제품 소유권이 이전된다.
- 거래 확정 즉시 다른 요청에서는 판매 불가 상태로 갱신한다.
- 다른 요청은 자동 거절되지 않고 기한까지 다른 제품으로 대응할 수 있다.
- 시스템이 제품을 복제하거나 거래를 되돌리지 않는다.
- 두 요청에 대한 동시 거래 확정은 허용하지 않는다.

제품 거래 잠금은 최종 확정 처리 동안만 사용하며, 미리보기 단계의 장기 예약으로 사용하지 않는다.

## 일반 영업과의 관계

활성 요청 수가 0개·1개·2개인지와 무관하게 `[대장간]`의 일반 영업은 계속 가능하다.

- 제작
- 강화·정밀강화·고위 정밀강화
- 수리·정비
- 보관함 관리
- 일반 판매
- 가게 오픈·영업 종료

두 요청이 모두 활성화돼 있어도 일반 판매는 차단하지 않는다.

다만 일반 판매 대상 제품이 하나 이상의 활성 요청 후보이면 다음 정보를 표시한다.

- 영향을 받는 요청 수
- 요청 고객 또는 요청 종류
- 해당 제품 판매 후 요청에서 사용할 수 없다는 사실
- 남은 대체 후보 제품 존재 여부

이 경고는 판매 금지가 아니라 정보 제공이다.

## 영업 종료와 기한 감소

명시적 영업 종료 시 활성 요청 각각의 남은 영업일을 독립적으로 정확히 1씩 감소시킨다.

```text
영업 종료
→ 요청 A 남은 영업일 2 → 1
→ 요청 B 남은 영업일 1 → 0
→ 요청 B 만료 결과 판정
→ 요청 A 활성 유지
→ 전체 요청 상태 무결성 저장
→ 다음 영업일 시작
```

원칙:

- 영업 종료 1회당 각 활성 요청의 기한 감소는 최대 1회다.
- 요청 A의 만료가 요청 B의 기한을 추가 감소시키지 않는다.
- 만료된 요청의 슬롯 해제와 남은 요청의 상태를 함께 일관되게 저장한다.
- 일부 요청만 기한이 감소한 중간 상태로 다음 영업일에 진입하지 않는다.
- 결과 연출 확인 순서가 슬롯 상태나 기한을 바꾸지 않는다.
- 앱 종료만으로 기한이나 슬롯이 변하지 않는다.

## 알림·내비게이션

`[방문 고객]` 탭은 활성 요청을 최대 2개까지 표시한다.

요청 카드 필수 정보:

- 고객 또는 요청 식별 정보
- 요청 장비 종류
- 주요 조건
- 남은 영업일
- 보상 방향
- 현재 대응 가능 제품 수
- 요청 상태

우선순위 표시:

1. 남은 영업일이 적은 요청
2. 필수 확인 상태가 있는 요청
3. 생성 시점이 빠른 요청

단, 표시 순서는 정보 우선순위이며 요청의 실제 결과나 보상을 바꾸지 않는다.

알림 배지 원칙:

- 활성 요청 수를 최대 2까지 표시할 수 있다.
- 단순 미확인 개수와 기한 임박 우선순위를 혼동하지 않는다.
- 남은 영업일 1인 요청은 기한·행동 우선 알림으로 올린다.
- 요청이 2개라는 이유로 일반 강화 입력을 중단하지 않는다.
- 자동으로 `[방문 고객]` 탭으로 강제 이동하지 않는다.

## 저장·복구 무결성

다음 상태는 함께 검증한다.

- 활성 요청 식별자 집합
- 활성 요청 수
- 각 요청의 남은 영업일
- 각 요청의 선택 중 제품
- 거래·거절·만료 적용 여부
- 슬롯 해제 여부
- 후속 세계 활동 연결 여부

금지되는 오류:

- 실제 활성 요청은 2개인데 UI는 1개만 표시
- 활성 요청 2개 상태에서 세 번째 요청 생성
- 거래 완료 요청이 활성 슬롯을 계속 점유
- 거래 완료·거절·만료 요청이 앱 재실행 후 다시 활성화
- 하나의 요청 종료로 두 슬롯이 해제됨
- 요청 A 상태 변경이 요청 B 기한·보상·제품 후보를 덮어씀
- 같은 제품을 두 요청에 중복 판매
- 후속 세계 활동이 요청 슬롯을 영구 점유

복구 시 활성 요청 수는 저장된 숫자만 신뢰하지 않고, 요청 상태 집합과 상호 검증한다.

## 접근성·성능

- 두 요청은 색상만으로 구분하지 않는다.
- 각 요청 카드에 고객·종류·기한·상태 텍스트를 제공한다.
- 화면 읽기 순서는 우선 요청 카드 전체를 읽은 후 다음 카드로 이동한다.
- 텍스트 확대 시 두 카드가 겹치지 않고 세로 스크롤로 접근 가능해야 한다.
- 요청 전환에 짧은 시간 제한 입력을 요구하지 않는다.
- 모션 감소 상태에서도 신규·임박·종료 상태 차이를 이해할 수 있어야 한다.
- 두 요청 데이터 표시가 강화 입력·프레임·저장 무결성을 저하시켜서는 안 된다.
- 불씨 정령은 요청 우선순위를 보조할 수 있지만 유일한 구분 수단이 아니다.

## 버티컬 슬라이스 검증 범위

최소 다음 시나리오를 검증한다.

1. 활성 요청 0개에서 첫 요청 발생
2. 활성 요청 1개에서 두 번째 요청 발생
3. 활성 요청 2개에서 추가 요청 미발생
4. 요청 하나 거래 완료 후 슬롯 해제
5. 요청 하나 거절 후 슬롯 해제
6. 요청 하나 만료 후 슬롯 해제
7. 한 요청 종료 후 다른 요청 상태 불변
8. 같은 제품이 두 요청 후보인 상태에서 한쪽 거래 확정
9. 영업 종료 시 두 요청 기한 독립 감소
10. 한 요청만 만료되고 다른 요청은 유지
11. 앱 종료·복귀 후 활성 요청 수와 기한 유지
12. 거래 후 후속 세계 활동은 유지되지만 요청 슬롯은 해제

## 현재 기획 상태 영향

이번 결정으로 해결되는 항목:

- 동시 활성 방문 고객 요청 상한
- 슬롯 점유 상태 정의
- 슬롯 포화 시 신규 요청 처리
- 요청 종료 후 슬롯 해제
- 두 요청의 독립 저장·기한·제품 충돌 계약

아직 미정인 항목:

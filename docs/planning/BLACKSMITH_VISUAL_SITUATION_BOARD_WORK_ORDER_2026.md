# 프로젝트 비주얼 중심 상황별 인게임 화면 명세 보드 작업지시문

> Decision ID: `BS-SCREEN-20260731-02`
>
> 상태: `USER_APPROVED / VISUAL_FIRST_WORK_ORDER`
>
> 적용 관계: `BS-SCREEN-20260731-01`의 상위 시각 산출물 계약
>
> Work Mode: `PLAN / REVIEW`
>
> 구현 권한: `NONE`

## 1. 목적

이 작업은 기술 감사 보고서가 아니라, **프로젝트가 구현되면 실제로 어떻게 보이는가**를 화면 중심으로 설명하는 명세 보드를 만든다.

최우선 질문:

1. 프로젝트의 비주얼 톤은 무엇인가?
2. 메인 화면은 어떻게 보이는가?
3. 핵심 플레이 화면은 어떻게 보이는가?
4. 인벤토리·자원 관리 화면은 어떻게 보이는가?
5. 결과 화면은 어떻게 보이는가?
6. 핵심 상황에서 화면이 어떻게 변하는가?
7. 플레이어는 무엇을 보고, 누르고, 이해해야 하는가?

기술 구조·데이터·테스트·위험 분석은 필요한 범위에서만 작성하며 PART D 부록으로 분리한다.

## 2. 확인 순서

1. 사용자 최신 요청
2. `AGENTS.md`

7. Goal·Issue·Planning 문서
8. 실제 Scene·Script·Resource·데이터
9. 기존 와이어프레임·UI 시안·이미지 자료

Base 원격은 반복 조회하지 않고 프로젝트 내부 동기화 사본을 우선한다. 문서와 실제 파일이 다르면 분리해서 보고한다.

## 3. 근거 수준 태그

모든 화면·요소·이미지에는 다음 중 하나를 표시한다.

- `CURRENT`: 실제 문서·파일·기존 시안에서 확인
- `INFERRED`: 확인 자료를 바탕으로 합리적으로 재구성
- `PROPOSED`: 필요한 신규 제안
- `PLACEHOLDER`: 임시 예시 시각 자료

CURRENT와 PROPOSED를 하나의 확정안처럼 섞지 않는다.

## 4. 최종 산출물

### PART A — 프로젝트 비주얼 기준 보드

- 핵심 경험: 장르, 플랫폼, 역할, 판타지, 감정, 세일즈포인트, 상징, 차별점
- 비주얼 방향: 그림체, 캐릭터, 배경, UI 스타일, 팔레트, 폰트 계층, 아이콘, 버튼·패널, 강조 효과, 금지 요소
- 확정·미정·제안 분리

설명은 짧게 유지하고 기술 표보다 비주얼 기준을 우선한다.

### PART B — 필수 기준 화면 4종 보드

1. 메인 화면
2. 전투 또는 핵심 플레이 화면
3. 인벤토리 또는 자원 관리 화면
4. 결과 화면

각 화면에 다음을 포함한다.

- SCREEN ID·화면명
- 화면 목적
- 핵심 행동
- 가장 중요한 정보 3개
- 이전·다음 화면
- 근거 수준
- 현재 구현 상태
- 판독 가능한 크기의 화면 예시

필수 상태 변형:

- 메인: 최초 실행, 저장 없음, 이어하기, 알림, 설정 복귀
- 핵심 플레이: 진입, 일반 조작, 위험 예고, 행동 선택, 조건 부족, 성공, 실패, 종료 직전
- 인벤토리: 빈 상태, 일반, 신규 획득, 비교, 사용·장착, 조건 미충족, 한도 초과
- 결과: 완전 성공, 부분 성공, 실패, 신규 해금, 재도전, 복귀

프로젝트에 맞지 않는 상태는 제외 이유를 적는다.

### PART C — 핵심 상황별 화면 시퀀스 보드

Vertical Slice 핵심 상황 3~5개를 선정하고, 각 상황을 4~8단계 화면 흐름으로 보여준다.

각 단계에는 다음을 표시한다.

- 새로 보이는 정보
- 사라지거나 비활성화되는 요소
- 플레이어 행동
- 강조 영역
- 캐릭터·카메라·UI 변화
- 성공·실패·전환 피드백
- 이전·다음 단계 연결

글 설명이 아니라 화면 변화가 중심이어야 한다.

### PART D — 구현 명세 부록

- Scene·Node·Resource·Signal·상태 머신 개요
- 화면 전환·저장·복귀
- 예외 처리·테스트
- 구현 우선순위·Codex Goal 후보

PART D는 SCREEN ID·SIT ID를 참조하며 메인 보드를 압도하지 않는다.

## 5. 시각화 규칙

- 한 장에 과도한 텍스트를 넣지 않는다.
- 화면을 판독 가능한 크기로 배치한다.
- 표보다 화면 예시와 흐름을 우선한다.
- 현재안과 개선안을 명확히 분리한다.
- 장르와 맞지 않는 generic 판타지 UI로 대체하지 않는다.
- 프로젝트 고유 감정·마스코트·자원·선택 구조를 화면에 반영한다.
- 공통 템플릿은 유지하되 프로젝트 전용 시각 언어를 보존한다.
- 큰 화면 보드 여러 장으로 나누는 것을 허용하며 한 장짜리 종합 대시보드를 강제하지 않는다.

## 6. 금지

- 기술 감사 보고서를 메인 산출물처럼 구성
- 필수 화면을 작게 축소
- CURRENT와 PROPOSED 혼합
- 근거 없는 아트 스타일 확정
- 필수 화면을 텍스트 목록으로만 제시
- 상황 시퀀스를 글로만 설명
- 모든 내용을 한 장에 밀어 넣기
- 프로젝트 고유 경험 대신 일반 게임 UI로 채우기

## 7. 적대적 검토루프

초안 후 아래 6단계를 순서대로 수행하고 FAIL이면 수정 후 재판정한다.

1. 화면 중심 산출물인가
2. 필수 4화면과 핵심 시퀀스가 즉시 보이는가
3. CURRENT/INFERRED/PROPOSED/PLACEHOLDER가 분리됐는가
4. 프로젝트 고유성이 살아 있는가
5. 화면 판독성과 첫 3초 정보 위계가 충분한가
6. 공통 템플릿과 프로젝트 전용 요소가 분리됐는가

## 9. Blacksmith 적용

Blacksmith 필수 대응 화면:

1. 대장간 허브·복귀
2. 단조·일반 강화·정밀강화 작업대
3. 보관함·재료·골드·보호·특수재료 관리
4. 제작·강화·고객·세계 결과와 장비 연대기

핵심 상황 시퀀스 후보:

- 첫 작품 단조와 제작 등급 확정
- 일반 강화에서 멈춤·도전·보호 판단
- +49에서 일반 정밀강화와 고위 정밀강화 비교
- 4개 고객 유형 중 이름 고객 요청과 작품 비교
- 판매 후 세계 결과와 연대기 귀환

Blacksmith의 `CURRENT`는 실제 PoC Scene·Script·데이터와 기존 시안에 한정한다. 목표 제품 UI, App Shell, 신규 허브, 유형별 복수 고객 화면, +50 이원화 화면은 실제 구현 전까지 `INFERRED` 또는 `PROPOSED`로 표시한다.

### Base 승격 후보

- PART A~D 공통 템플릿

### Blacksmith 전용 유지

- 대장간·화로·모닥 시각 언어
- 제작 등급·강화 위험·정밀강화 비교
- 고객 4유형×복수 이름 고객
- 장비 소유권·세계 결과·연대기
- 일반/고위 +50 경로 연출

## 11. 완료 기준

- 프로젝트 구현 모습을 한눈에 이해할 수 있다.
- 필수 화면 4종이 크게 보인다.
- 핵심 상황의 화면 변화가 시각적으로 드러난다.
- 비주얼·UI·UX 방향이 정리된다.
- 근거 수준이 분리된다.
- 기술 부록이 메인 보드를 압도하지 않는다.
- 다른 프로젝트에 재사용할 공통 구조와 Blacksmith 전용 요소가 분리된다.
- 적대적 검토 전 항목이 PASS다.

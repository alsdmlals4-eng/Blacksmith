## 일반 방문 고객 발생 확률

일반 `[방문 고객]` 요청은 **기본 발생 확률 40% + 연속 2회 미발생 후 다음 적격 영업일 확정 발생** 구조를 사용한다.

이 구조는 방문 고객이 매일 강제로 등장하는 의무 콘텐츠가 되는 것을 막으면서도, 긴 기간 동안 요청이 전혀 발생하지 않는 극단적인 공백을 제한한다.

```text
적격 영업일 시작
→ 일반 방문 고객 발생 판정

40% 성공
→ 신규 요청 1개 생성
→ 연속 미발생 누적 0으로 초기화

60% 미발생
→ 연속 미발생 누적 +1

연속 미발생 누적 2
→ 다음 적격 영업일 신규 요청 1개 확정 발생
→ 누적 0으로 초기화
```

## 적격 영업일 정의

다음 조건을 모두 만족하는 영업일만 일반 발생 확률과 연속 미발생 누적 계산에 참여한다.

- 영업일 시작 처리 단계에 진입함
- 활성 방문 고객 요청이 0개 또는 1개임
- 해당 영업일 신규 요청 판정을 아직 수행하지 않음
- 대기 중인 중요 고객 확정 트리거가 해당 영업일에 요청을 생성하지 않음
- 저장 복구·무결성 오류로 영업일 시작 처리가 중단되지 않음

```text
적격 영업일
= 빈 요청 슬롯 존재
+ 당일 판정 미수행
+ 중요 고객 확정 생성 없음
+ 정상적인 영업일 시작 처리
```

다음 영업일은 일반 확률 판정의 적격 영업일로 계산하지 않는다.

- 활성 요청이 이미 2개인 영업일
- 중요 고객 확정 트리거로 신규 요청이 생성된 영업일
- 테스트 시나리오 전용 확정 요청이 생성된 영업일
- 영업일 시작 처리 중 저장 복구 또는 무결성 오류가 발생한 영업일

## 기본 발생 확률

버티컬 슬라이스의 초기 기획 기준은 다음과 같다.

- 일반 방문 고객 기본 발생 확률: `40%`
- 판정 시점: 영업일 시작 시 최대 1회
- 발생 시 생성 수: 최대 1개
- 미발생 허용: 예
- 행동 반복에 의한 추가 판정: 금지
- 앱 재실행에 의한 재판정: 금지

기본 40%는 구현 상수가 아니라 초기 밸런스 기준이다. 실제 플레이테스트 결과에 따라 조정할 수 있으나, 조정 시에도 연속 미발생 보정 구조와 저장·무결성 계약은 유지한다.

## 연속 미발생 보정

일반 발생 판정이 실제로 수행됐지만 신규 요청이 생성되지 않은 경우에만 `연속 미발생 누적`을 1 증가시킨다.

```text
첫 번째 적격 영업일 미발생
→ 누적 1

두 번째 적격 영업일 미발생
→ 누적 2

다음 적격 영업일
→ 확률 판정 대신 일반 요청 1개 확정 생성
→ 누적 0
```

### 확정 발생 시점

누적이 2가 된 바로 그 영업일에 요청을 추가 생성하지 않는다.

```text
영업일 N
→ 일반 판정 미발생
→ 누적 2 저장
→ 당일 추가 생성 없음

다음 적격 영업일 N+1
→ 보정 확정 발생
```

이는 영업일당 신규 요청 최대 1개 계약을 보존하고, 한 번의 판정 결과가 같은 영업일에 다시 뒤집히는 것을 방지한다.

## 누적값 증가·유지·초기화 규칙

### 누적 증가

다음 조건에서만 누적을 1 증가시킨다.

- 적격 영업일임
- 일반 발생 판정을 실제 수행함
- 중요 고객 확정 트리거가 아님
- 신규 일반 요청이 생성되지 않음
- 판정 결과가 원자적으로 저장됨

### 누적 유지

다음 상황에서는 누적값을 증가시키거나 초기화하지 않고 그대로 유지한다.

- 활성 요청 2개로 일반 판정을 생략함
- 중요 고객 확정 트리거가 요청을 생성함
- 테스트용 확정 트리거가 요청을 생성함
- 영업일 시작 처리 전에 앱이 종료됨
- 저장 복구·무결성 오류 때문에 판정을 완료하지 못함
- 일반 요청 발생 자격이 없는 영업일임

```text
슬롯 포화
→ 일반 판정 없음
→ 누적 유지

중요 고객 확정 등장
→ 일반 판정 없음
→ 누적 유지
```

### 누적 초기화

다음 상황에서 누적을 0으로 초기화한다.

- 일반 확률 판정으로 요청이 생성됨
- 연속 미발생 보정으로 일반 요청이 확정 생성됨

중요 고객 확정 트리거로 요청이 생성된 경우에는 일반 누적을 초기화하지 않는다. 중요 고객의 서사 등장 때문에 일반 방문 고객의 누적 보정 진행이 사라지지 않도록 한다.

## 중요 고객 확정 트리거와의 관계

영업일 시작 시 대기 중인 중요 고객 확정 트리거가 있으면 일반 확률 및 보정 판정보다 우선한다.

```text
영업일 시작
→ 빈 슬롯 확인
→ 중요 고객 확정 트리거 확인

확정 트리거 존재
→ 중요 고객 요청 1개 생성
→ 당일 일반 확률 판정 없음
→ 일반 미발생 누적 유지

확정 트리거 없음
→ 누적 2 여부 확인
→ 보정 확정 발생 또는 기본 40% 판정
```

중요 고객 요청과 일반 고객 요청을 같은 영업일에 각각 하나씩 생성하지 않는다.

## 슬롯 포화와의 관계

활성 방문 고객 요청이 2개이면 일반 발생 판정을 수행하지 않는다.

- 미발생 누적을 증가시키지 않음
- 누적을 초기화하지 않음
- 숨은 요청을 생성하지 않음
- 보정 확정 발생 기회를 소비하지 않음
- 슬롯이 빈 다음 적격 영업일에 기존 누적값을 이어서 적용

```text
누적 2
→ 활성 요청 2개
→ 보정 대기 유지
→ 요청 하나 종료
→ 다음 영업일 시작
→ 일반 요청 확정 발생
```

슬롯이 영업일 도중 비더라도 당일 추가 판정은 없다. 다음 영업일 시작에만 보정 또는 일반 판정을 수행한다.

## 판정 순서

일반 요청 생성 판정의 권장 순서는 다음과 같다.

```text
1. 이전 영업 종료 체크포인트 복구
2. 미확인 비가역 결과 정리
3. 요청 거래·거절·만료 상태 정리
4. 활성 요청 수 계산
5. 당일 신규 요청 판정 수행 여부 확인
6. 대기 중 중요 고객 확정 트리거 확인
7. 중요 고객 생성 여부 결정
8. 중요 고객이 없으면 일반 미발생 누적 확인
9. 누적 2면 보정 확정 발생
10. 누적 2 미만이면 기본 40% 판정
11. 요청 또는 미발생 결과와 누적값 원자적 저장
12. 일반 영업 조작 허용
```

## 저장 계약

영업일 요청 발생 상태에 최소 다음 정보를 저장한다.

- 현재 영업일 식별자
- 당일 신규 요청 판정 수행 여부
- 판정 경로
  - 슬롯 포화 생략
  - 중요 고객 확정 트리거
  - 일반 확률 판정
  - 연속 미발생 보정 확정
- 판정 결과
  - 발생
  - 미발생
  - 생략
- 판정에 사용한 일반 발생 확률 버전 또는 설정 식별자
- 판정 전 연속 미발생 누적값
- 판정 후 연속 미발생 누적값
- 생성된 요청 식별자
- 생성 결과 저장 완료 여부

### 원자성

다음 상태를 하나의 일관된 결과로 저장한다.

```text
발생 여부 판정
+ 신규 요청 데이터
+ 당일 판정 완료 표식
+ 연속 미발생 누적 변경
```

금지되는 중간 상태:

- 요청은 생성됐지만 누적이 초기화되지 않음
- 누적은 증가했지만 당일 판정 완료 표식이 없음
- 당일 판정 완료 표식은 있으나 발생·미발생 결과가 없음
- 보정 확정 발생이 저장됐지만 요청 데이터가 없음
- 앱 재실행으로 같은 영업일 판정을 다시 실행함
- 저장 복구 후 다른 확률 결과로 변경됨

## 무작위 판정 무결성

- 일반 요청 발생 여부는 영업일당 정확히 한 번 판정한다.
- 판정 결과 저장 전 요청 발생 연출을 시작하지 않는다.
- 연출, 불씨 정령 반응 또는 화면 전환이 발생 여부를 결정하지 않는다.
- 앱 강제 종료 후 같은 발생·미발생 결과로 복귀한다.
- 세이브 재로드로 40% 판정을 반복해 원하는 결과를 고르는 구조를 금지한다.
- 테스트 빌드의 강제 발생 기능은 일반 확률 경로와 명확히 구분한다.

## 사용자 정보 표시

일반 캠페인에서는 정확한 40% 수치나 내부 미발생 누적을 플레이어에게 반드시 공개할 필요는 없다.

다만 다음 원칙을 지킨다.

- 요청이 없는 날을 오류로 표현하지 않음
- 슬롯 포화 중 놓친 고객이 존재하는 것처럼 표현하지 않음
- 보정 확정 발생을 특별 보상이나 운명 보장처럼 과장하지 않음
- 앱 재실행으로 발생 결과가 달라질 것처럼 암시하지 않음
- 디버그·테스트 화면에서는 판정 경로와 누적값을 확인할 수 있어야 함

정확한 확률 공개 여부는 일반 UI·경제 정보 공개 원칙의 후속 결정으로 남긴다.

## 고객·장비 종류·보상 선택과 분리

이번 결정은 요청이 **발생하는지 여부**만 확정한다.

다음 항목은 별도 생성 단계에서 결정한다.

- 고객 유형 또는 이름 있는 고객
- 요청 장비 종류·범주
- 최소 조건과 선호 방향
- 제안 가격과 보상
- 관계·약속·후속 세계 활동 가능성
- 현재 활성 요청과의 중복 억제

발생 확률 성공이 현재 보관함에 맞는 장비가 존재함을 보장하지 않는다. 고객 요청을 충족하기 위해 새 제품을 제작·강화할 수 있는 2영업일 기한 계약을 그대로 사용한다.

## 버티컬 슬라이스 검증

버티컬 슬라이스에서는 다음 시나리오를 검증한다.

1. 기본 확률 판정으로 일반 요청 발생
2. 기본 확률 판정 미발생 후 누적 1 저장
3. 두 번째 미발생 후 누적 2 저장
4. 다음 적격 영업일 보정 확정 발생
5. 누적 2 상태에서 슬롯 2개 포화 시 누적 유지
6. 슬롯 해제 후 다음 영업일 보정 발생
7. 중요 고객 확정 생성일에 일반 누적 유지
8. 앱 종료·복귀 후 같은 판정 결과와 누적값 유지
9. 요청 발생 저장 중 오류가 발생해도 중복 요청 없음
10. 요청 미발생 영업일에도 제작·강화·일반 판매 정상 진행

테스트를 위해 확률 결과를 고정하거나 누적값을 설정할 수 있으나, 이는 명시적으로 표시된 테스트 픽스처이며 일반 캠페인 발생 규칙과 구분한다.

## 현재 기획 상태 영향

이번 결정으로 해결되는 항목:

- 일반 신규 요청의 초기 발생 확률 기준
- 장기 미발생 방지 구조
- 슬롯 포화일의 누적 처리
- 중요 고객 확정 등장일의 누적 처리
- 발생 결과와 누적값의 저장 원자성

아직 미정인 항목:

- 고객 유형·장비 종류·보상 가중치
- 같은 장비 종류 또는 고객 유형의 연속 중복 억제
- 여러 중요 고객 확정 트리거의 우선순위
- 일반 발생 확률의 플레이어 공개 여부
- 버티컬 슬라이스 대표 고객 이벤트 조합
- 일반 영업과 방문 고객 이벤트를 포함한 15~25분 세션 예산

```text
GENERAL_VISITING_REQUEST_BASE_PROBABILITY: FORTY_PERCENT
GENERAL_VISITING_REQUEST_PITY_MODEL: GUARANTEED_AFTER_TWO_ELIGIBLE_MISSES
CONSECUTIVE_MISS_THRESHOLD: TWO
GUARANTEED_REQUEST_TIMING: NEXT_ELIGIBLE_OPERATING_DAY
SAME_DAY_MISS_CONVERTS_TO_REQUEST: FORBIDDEN
SLOT_FULL_DAY_COUNTS_AS_MISS: NO
IMPORTANT_TRIGGER_DAY_COUNTS_AS_MISS: NO
```

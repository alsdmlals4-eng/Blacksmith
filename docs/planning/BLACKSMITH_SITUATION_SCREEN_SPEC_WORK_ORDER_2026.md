## 1. 작업 목적

현재 프로젝트의 기획 문서, 시스템 문서, 데이터 구조와 실제 파일을 분석해 플레이어가 실제 진행 중 마주치는 대표 상황을 도출한다.

각 상황을 다음 흐름으로 구현 가능한 명세로 만든다.

```text
상황
→ 플레이어 판단
→ 입력
→ 시스템 반응
→ 결과
→ 다음 상황
```

이 작업은 단순 UI 화면 목록이나 콘셉트 이미지 제작이 아니다. 현재 단계에서는 제품 코드·Scene·런타임 데이터·에셋을 직접 구현하지 않고, 화면 구조·시스템 연결·데이터 경계·구현 범위·검증 기준만 설계한다.

## 2. 확인 순서와 권한

작업 시작 전에 다음 순서로 확인한다.

1. 사용자의 최신 지시
2. 프로젝트 루트 `AGENTS.md`
3. `docs/BASE_RULES_VERSION.md`
4. `[기획서]/00_프로젝트_허브/DOCUMENTATION_MAP.md`
5. 프로젝트에 동기화된 Base 로컬 사본·어댑터·스냅샷·라우터
6. 프로젝트 전용 규칙·README·권위 문서
7. 현재 Goal·Issue·작업 계획
8. 실제 Scene·Script·Resource·데이터 파일

일상 작업마다 Base 원격 저장소 전체를 반복 조사하지 않는다. 프로젝트 내부의 고정 Base 버전과 동기화 사본을 우선하고, 버전 불일치·누락·권위 충돌이 있을 때만 원격 Base 확인을 수행한다.

문서와 실제 구현이 충돌하면 다음을 분리한다.

- `확정`: 현행 권위 문서 또는 실제 파일에서 확인
- `실제 구현`: Scene·Script·Resource·데이터에서 확인
- `해석`: 확정 사실로부터 도출
- `가정`: 명세 완성을 위한 임시안
- `제안`: 신규 설계이며 승인 전 비정본
- `미구현`: 문서에는 있으나 실제 파일에 없음
- `확인 필요`: 사용자 결정이 필요한 사항

## 3. 프로젝트 핵심 정의

화면 설계 전 다음을 먼저 작성한다.

- 장르
- 플랫폼
- 예상 플레이 세션
- 플레이어 역할
- 핵심 판타지
- 핵심 감정
- 주요 선택과 고민
- 주요 보상
- 기억에 남아야 할 장면
- 대표 세일즈포인트
- 마스코트·상징 요소
- 유사 장르와의 차별점

핵심 플레이 루프는 다음 형식으로 기술한다.

```text
게임 시작
→ 첫 행동
→ 정보·자원 획득
→ 판단
→ 선택·조작
→ 위험·비용
→ 결과 확인
→ 성장·상태 변화
→ 다음 목표
```

## 4. 화면 설계 원칙

모든 화면은 다음 중 하나 이상을 수행해야 한다.

- 현재 상황 이해
- 중요한 선택 제시
- 위험과 보상 비교
- 행동 결과의 명확한 피드백
- 캐릭터·작품·세계에 대한 감정 형성
- 다음 행동 동기 제공

역할이 없는 화면, 동일 정보를 반복하는 화면, 핵심 플레이를 가리는 장식 화면은 만들지 않는다.

## 5. 필수 기준 화면 4종

대표 상황을 자유롭게 도출하기 전에 다음 기준 화면을 먼저 조사한다.

1. 메인 화면
2. 전투 또는 프로젝트의 핵심 플레이 화면
3. 인벤토리 또는 보유 자원 관리 화면
4. 결과 화면

전통적인 전투·인벤토리가 없으면 기능을 발명하지 않고 실제 프로젝트에서 대응하는 화면을 사용한다. 대응 화면이 없으면 `해당 없음`, `현재 미정`, `신규 제안` 중 하나로 표시한다.

### Blacksmith 초기 대응 가설

| 기준 화면 | Blacksmith 대응 화면 | 현재 상태 |
|---|---|---|
| 메인 화면 | 대장간 허브·가게 오픈·영업일 진입 | 실제 파일 재확인 필요 |
| 핵심 플레이 화면 | 단조 작업대·강화 작업대·+49→+50 경로 비교 | 문서 확정과 기존 PoC 구현 분리 필요 |
| 보유 자원 관리 | 보관함·재료·골드·보호석·특수재료 관리 | 실제 Scene·데이터 재확인 필요 |
| 결과 화면 | 단조/강화 결과·판매 결과·고객 세계 환류·장비 연대기 | 단일 화면인지 상태별 화면인지 재판정 필요 |

이 표는 작업 시작점이며 실제 파일과 충돌하면 실제 구조를 우선해 수정한다.

각 기준 화면마다 다음을 조사한다.

- 문서 정의와 실제 Scene/UI/Script/Resource/데이터
- 구현·임시 UI·미구현 상태
- 그림체·배경·UI 스타일·색·폰트·아이콘·패널·버튼·전환
- 플레이어 목적·빈번한 행동·첫 정보·입력 수·취소·복귀·접근성
- 현재 확인 와이어프레임과 개선 제안 와이어프레임
- 구성요소 표
- 최초 진입·일반·선택 중·빈 상태·잠김·신규·최대치·오류·전환·튜토리얼 상태
- 화면 간 연결·저장·로딩·중복 입력 방지
- Godot Scene·Node·Resource·Signal·상태 머신·입력·해상도·오디오
- 완료 기준

## 6. 대표 상황 도출과 우선순위

상황은 메뉴명이 아니라 특정 플레이 맥락과 목적이 있는 순간으로 정의한다.

예시 형식:

```text
SIT-001 — 첫 단조를 시작해 타격·열·피버를 이해하는 순간
SIT-002 — 강화 결과표를 보고 멈춤·도전·보호를 선택하는 순간
SIT-003 — +49 작품에서 일반 정밀과 고위 정밀을 비교하는 순간
SIT-004 — 방문 고객 요청과 보관함 작품을 비교하는 순간
SIT-005 — 작품이 고객의 세계 활동에 기여한 결과를 확인하는 순간
```

의미 없는 숫자만 사용하지 않고 ID 옆에 상황명을 반드시 병기한다.

상황 유형:

- 첫인상·진입
- 탐색·정보 확인
- 대화·관계
- 선택·준비
- 핵심 플레이·제작·강화
- 위험·실패·부분 성공·완전 성공
- 보상·성장·복귀
- 반복 플레이·장기 진행

우선순위 평가표:

| 상황 | 발생 빈도 | 핵심 재미 | 감정 중요도 | 구현 위험 | 차별성 | 우선순위 |
|---|---:|---:|---:|---:|---:|---|

- `P0`: Vertical Slice 핵심
- `P1`: 핵심 경험 완성
- `P2`: 다양성·편의
- `P3`: 폴리싱·확장

P0만 먼저 상세 명세한다. P1~P3는 요약 후 필요할 때 확장한다.

## 7. 상황별 상세 명세 공통 형식

각 P0 상황은 아래 A~T 구조를 동일하게 사용한다.

### A. 상황 개요

발생 이유, 현재 목표, 알고 있는 정보, 모르는 정보, 위험, 보상, 감정, 핵심 선택, 다음 상황을 기록한다.

### B. 근거와 가정

`확정 / 실제 구현 / 해석 / 가정 / 제안 / 확인 필요`를 분리한다.

### C. 진입 조건

이전 상태, 트리거, 진행 플래그, 플레이어·월드 상태, 진입 불가·중복 방지 조건을 작성한다.

### D. 화면 목적

플레이어가 가장 먼저 볼 정보부터 행동 후 확인 정보까지 우선순위를 정한다.

### E. 예상 인게임 화면

이미지를 만들기 전에 텍스트 와이어프레임을 작성한다. 화면 비율, 카메라, 플레이 공간, HUD, 정보·입력·팝업·위험·결과 영역, 강조 요소, 첫 3초 정보를 포함한다.

### F. 화면 구성요소

| 요소 | 역할 | 표시 조건 | 숨김 조건 | 입력 가능 | 우선순위 |
|---|---|---|---|---|---|

배경, 캐릭터, 안내자, 고객, 장비, 상호작용 대상, 목표, 자원, 버튼, 선택지, 대사, 튜토리얼, 위험, 보상, 결과, 일시정지·뒤로 가기를 검토한다.

### G. 플레이어 입력

| 입력 | 발생 조건 | 시스템 반응 | 시각 피드백 | 실패·제한 |
|---|---|---|---|---|

Blacksmith는 모바일 터치를 우선한다. PC·컨트롤러 입력은 현재 플랫폼 계약에 없으면 제외하거나 미래 제안으로 표시한다. 선택, 확인, 취소, 드래그, 길게 누르기, 빠른 행동과 화면 전환 입력을 구분한다.

### H. 상황 진행 흐름

진입부터 데이터 갱신·다음 상황까지 단계별로 작성하고 각 단계에 자동/입력 필요/취소/저장/실패/반복 가능 여부를 표시한다.

### I. 시스템 반응

| 행동 | 조건 | 즉시 반응 | 데이터 변화 | 장기 영향 | 다음 상태 |
|---|---|---|---|---|---|

정상뿐 아니라 자원 부족, 잘못된 대상, 중복 입력, 취소, 시간 초과, 실패, 부분 성공, 완전 성공을 포함한다.

### J. 필요한 시스템

| 시스템 | 역할 | 입력 데이터 | 출력 데이터 | 연결 시스템 |
|---|---|---|---|---|

제작·강화·보관함·고객 요청·적합도·소유권·장비 연대기·세계 결과·저장·오디오·튜토리얼·카메라·UI 상태 시스템을 실제 필요 범위에서만 연결한다.

### K. Godot 구현 구조

Godot 4.x 기준 Scene·Node 구조를 텍스트 트리로 작성한다. 각 Node의 책임, 보유 데이터, 통신 방식, Scene 분리, 재사용 가능성, 기존 구조 연결 가능성을 설명한다.

### L. Scene 분리 기준

다음 중 추천 방식을 선택하고 이유를 제시한다.

1. 완전 별도 Scene
2. 기존 Scene 내부 상태 전환
3. CanvasLayer 오버레이
4. 재사용 UI Scene 인스턴스
5. SubViewport·별도 렌더 영역

### M. Signal과 상태 전환

개념 Signal과 상태 머신을 작성한다.

```text
ENTER → INTRO → PLAYER_CONTROL → ACTION_SELECTION → RESOLVING → RESULT → EXIT
```

각 상태의 진입 조건, 입력, 종료 조건, 유지 데이터, 취소 가능 여부를 포함한다.

### N. 데이터 구조

| 데이터 | 주요 필드 | 저장 위치 | 변경 주체 | 저장 필요 |
|---|---|---|---|---|

기존 Resource·JSON·Google Sheet 구조의 확장을 먼저 검토한다. 새 포맷은 기존 구조로 표현할 수 없다는 증거가 있을 때만 제안한다.

### O. 화면 전환 유지 데이터

플레이어 자원, 장비 ID·상태·강화 이력, 선택 결과, 진행 플래그, 고객·월드 상태, 카메라, BGM, 일회 연출, 복귀 화면을 `반드시 유지 / 종료 초기화 / 세이브 기록 / 세션 전용`으로 구분한다.

### P. 연출 명세

화면 전환, 카메라, 장비·캐릭터 애니메이션, UI 순서, 강조, 성공·실패, BGM·SFX·진동·흔들림을 작성한다. 연출은 판정·위험·비용 정보를 가리지 않는다.

### Q. 필요한 애셋

| 애셋 | 용도 | 상태·변형 | 우선순위 | 임시 대체 가능 |
|---|---|---|---|---|

### R. 예외 상황

연속 입력, 전환 중 입력, 조건 변경, 대상 제거, 데이터 누락, 저장·재진입, 해상도 변경, 일시정지, 앱 종료 복구, 오디오 중복, 애니메이션·판정 불일치를 방어한다.

### S. 완료 기준

목표·행동 가능 여부·즉시 피드백·화면과 데이터 일치·다음 상태·재진입·저장·지원 해상도·접근성 기준을 모두 만족해야 한다.

### T. 테스트 체크리스트

정상, 실패, 반복·저장, 화면·입력 흐름으로 나눠 체크박스를 작성한다.

## 8. 전체 상황 연결과 화면 보드

모든 상황은 전체 흐름에 연결한다.

```text
게임 시작
→ 대장간 허브
→ 단조·강화 목표 선택
→ 재료·보관함 확인
→ 핵심 작업
→ 위험 선택
→ 결과
→ 판매·고객 요청
→ 세계 환류·연대기
→ 성장·복귀
```

| 이전 상황 | 전환 조건 | 다음 상황 | 유지 데이터 | 전환 방식 |
|---|---|---|---|---|

주요 상황 6~9개는 한 장짜리 화면 보드로 요약한다.

- 화면명·상황명
- 텍스트 와이어프레임
- 핵심 행동
- 가장 중요한 정보
- 그림체·UI 기준
- 주요 시스템
- 이전·다음 상황
- 우선순위
- 실제 구현 상태

## 10. 중간점검 적용 규칙

- 현재 고객 4유형·+50 이원화 정합화 작업을 먼저 마감한다.
- 그다음 이 작업지시문으로 Blacksmith 중간점검을 시작한다.
- 중간점검은 실제 코드를 작성하지 않는다.
- 문서상 확정·실제 구현·미구현·가정·제안을 분리한다.
- 먼저 네 기준 화면의 실제 파일 현황을 감사한다.
- P0 상황을 확정하기 전 벤치마킹과 적대적 검토를 수행한다.
- 결과에서 발견한 승인 결정은 `BS-SYNC-20260731-01`에 따라 GitHub·계획 데이터·Sheet에 같은 Decision ID로 즉시 동기화한다.

## 11. Base 승격 후보

공용화 후보:

- 필수 기준 화면 4종을 프로젝트 대응 화면으로 치환하는 절차
- 화면과 상황을 분리하지 않는 `SCREEN → SIT` 구조
- A~T 상황 명세 형식
- 문서·실제 구현·가정·제안 분리
- P0 우선 상세화와 6~9개 화면 보드
- Godot Scene·Node·Resource·Signal·저장·테스트 연결

Blacksmith 전용으로 유지할 항목:

- 대장간 허브·단조·강화·보관함 대응
- +5/+10과 +49→+50 일반·고위 정밀강화
- 고객 4유형×복수 고객
- 장비 소유권·연대기·세계 환류
- 모바일 세로형 Android 입력·정보 위계

Base 반영은 다른 프로젝트에서 반복 유효성이 확인되고 별도 Base 승인·PR을 거친 뒤 수행한다.

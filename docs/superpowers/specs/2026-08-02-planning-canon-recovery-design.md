## 1. 승인된 작업 방향

Blacksmith는 기존 Draft PR #81을 그대로 병합하지 않는다. 현재 `main`에서 새 작업선을 시작해 다음 두 단계를 분리한다.

```text
1단계: 운영·정본 복구
→ 2단계: 승인 기획 선별 승격·총기획 작성
→ 적대적 검토와 Grill Me
→ 사용자 기획 완료
→ 최종 검수
→ 사용자 검수 완료
→ 별도 Codex 구현 인계
```

이 설계는 문서 수를 늘리는 것이 목적이 아니다. 현재 승인 방향, 실제 구현, GitHub 책임 원본, Google Sheet, 다음 작업을 새 작업자가 저장소만으로 복원할 수 있게 만드는 것이 목적이다.

## 2. 이번 승인으로 확정된 운영 규칙

### 2.1 기획 우선

- 지금부터 제품 구현보다 기획 작성과 정본 정합을 우선한다.
- 전체 기획·적대적 최종 검수·사용자 검수 완료 전 Codex 제품 구현을 시작하지 않는다.
- 기존 PoC 코드·Scene·데이터는 구현 사실과 회귀 기준선으로 보존하되 최신 기획의 완료 증거로 사용하지 않는다.

### 2.2 상세 데이터·수치

- 기술 세부, 시험값, 초기 밸런스값, UI 간격·시간·확률 초안 등은 GPT 권장안을 기본값으로 사용한다.
- 이러한 값은 처음부터 확정 수치로 위장하지 않고 `RECOMMENDED_DEFAULT` 또는 `TEST_VALUE`로 기록한다.
- 플레이어 선택 의미, 난이도 곡선, 경제 속도, 세션 길이, 보상 체감을 근본적으로 바꾸는 수치는 적대적 검토 후에도 중요 기획으로 판정되면 Grill Me 대상이 될 수 있다.
- 검증 전 시험값은 플레이테스트·시뮬레이션·런타임 결과에 따라 조정 가능해야 한다.

### 2.3 Grill Me

다음에만 사용자 질문을 한다.

- 프로젝트 코어·플레이어 판타지·뾰족한 재미를 바꾸는 선택
- 두 승인 기획 또는 시스템 원칙이 양립하지 않는 충돌
- 버티컬 슬라이스·데모·본제작 범위를 다르게 만드는 선택
- 주요 실패·파괴·복구·보상 의미를 바꾸는 선택
- 기존 승인 Decision을 대체해야 하는 경우
- 둘 이상의 유효한 개선안이 플레이 경험·제작 범위·사업 방향을 다르게 만드는 경우

질문은 한 번에 하나의 독립 결정만 다루며 다음 형식을 사용한다.

```text
확인된 공백·충돌
→ 기존 정본과 실제 구현
→ 보호할 강점
→ 선택지별 장단점·영향
→ Evidence와 반증
→ GPT 권장안
→ 확정 시 갱신할 정본·소비자·검증
```

저장소·Sheet에서 확인할 수 있는 사실, 이미 승인된 결정, 기술 세부와 시험값은 다시 묻지 않는다.

## 6. 2단계 — 승인 기획 선별 승격·총기획 작성

### 승격 분류

PR #81의 항목을 다음으로 분류한다.

- `CONFIRMED_WITH_APPROVAL_EVIDENCE`: 사용자 승인 원문·Decision ID·책임 원본이 복원됨
- `CONFIRMED_BY_LATEST_USER_DIRECTION`: 이번 사용자 지시가 명시적으로 확정함
- `RECOMMENDED_DEFAULT`: 방향을 바꾸지 않는 기술·수치 기본값
- `PROPOSED_REVIEW_REQUIRED`: 내용은 유효해 보이나 승인 증거가 부족함
- `USER_DECISION_REQUIRED`: 중요 기획 충돌 또는 방향 선택
- `RESEARCH_OR_TEST_REQUIRED`: 재미·밸런스·성능·접근성 등 실행 증거 필요
- `HISTORY_ONLY`: 대체된 결정·과거 Gate·과거 Base 이관 계획

## 7. 적대적 검토 루프

모든 주요 기획 묶음은 다음 순서를 통과한다.

```text
Attack
→ Validate Critique
→ 개선안 2~3개 비교
→ AUTO_FIX / GRILL_ME / RESEARCH_OR_TEST 분류
→ 승인된 최소 개선
→ 정본·Sheet 동기화
→ Regression Recheck
```

필수 공격 관점:

- 플레이어 약속과 실제 반복 행동이 같은가
- +5/+10 일상 루프와 +50 장기 목표가 서로를 약화하지 않는가
- 자동화가 작품 정체성·위험 선택·소유권 결정을 우회하지 않는가
- 고객·세계 결과가 직접 전투 게임으로 범위 팽창하지 않는가
- 장비 애착과 파괴 위험이 불공정·복구 불가능 피로로 변하지 않는가
- 모바일 정보량과 수식어·연대기·고객 적합 정보가 양립하는가
- 저장·ResultEnvelope·마이그레이션 계약이 모든 비가역 결과에 적용되는가
- 버티컬 슬라이스가 1인 개발과 대표 품질을 동시에 감당할 수 있는가
- PC 고려가 모바일 UX·범위를 조기에 복잡하게 만들지 않는가
- 기획 문서만 존재하고 실제 구현·검증 경로가 없는 기능이 남지 않는가

## 8. 중요 Grill Me 후보

다음은 감사·증거 재검증 후 실제 충돌로 확인될 때만 한 건씩 질문한다.

1. 15~25분 버티컬 슬라이스 안에 준비된 +49 작품의 +50 경로까지 포함할지, +5/+10 첫 작품 루프와 분리할지
2. 파괴 위험이 장비 애착의 핵심인지, 고객 소유 장비·장기 작품에는 별도 보호 경계를 둘지
3. 고객·세계 환류를 대표 결과 연출 중심으로 제한할지, 플레이 가능한 외부 장소·직접 전투로 확장할지
4. 모바일 출시 범위에서 PC 대응을 데이터·입력 추상화만 준비할지, 동시 UI 품질 기준까지 포함할지
5. 장기 목표의 중심을 +50 이후 작품 심화에 둘지, 고객 관계·명작 전당·세계 사건의 병렬 성장으로 둘지

이미 승인된 결정과 동일하거나 기술 기본값으로 해결되는 항목은 질문하지 않는다.

## 12. 다음 Gate

이 문서에 대한 사용자 검토가 완료되면 `writing-plans`로 1단계 운영·정본 복구 실행 계획을 작성한다. 계획 승인 후에만 운영 문서·Registry·Adapter·Google Sheet를 실제 수정한다.
